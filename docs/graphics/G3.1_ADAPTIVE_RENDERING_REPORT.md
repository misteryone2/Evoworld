## 2. Problemi trovati

### P0 — Nessun difetto bloccante
Nessuna perdita di dati, alterazione della biologia o regressione del percorso G3.

### P1 — Costo del renderer (confermato dalla profilazione)
1. **Il loop aggiorna ogni creatura ogni frame**, anche quando la sua posizione sullo schermo non cambia in modo percettibile o è fuori visuale. A 10 000 creature il costo CPU è dominato da:
   - `animationTrack` ~9,1 ms
   - `matrixWrites` ~8,4 ms
   - `poseFull` ~5,3 ms
   - `genericPartsApprox` ~3,1 ms
   - `colorWrites` ~2,7 ms
   - `planFor` + `planValidate` ~3,3 ms
2. **Nessun culling per-creatura**: `configureInstancedMesh` disabilita il frustum culling su tutte le mesh instanziate (correttamente, per evitare la sfera di ingombro vuota), ma questo significa che anche le creature dietro la camera vengono calcolate e scritte.
3. **Nessuna distinzione vicino/lontano nel loop**: il LOD dell'animazione (`lib/animationLod.ts`) esiste già, ma non riduce la frequenza di aggiornamento dei buffer.
4. **`syncFrame/regenerate` è il costo singolo più alto** (1 702 ms a 10 000 creature) ma avviene solo quando cambiano i dati MOR, non ogni frame: non è un target dell'ottimizzazione per-frame.

### P2 — Varianza delle misure
Le esecuzioni sequenziali dello stesso benchmark su questa macchina mostrano varianza elevata (es. `g2-optimized/10000`: 101,5 ms in una run, 211,4 ms in un'altra). Per questo il confronto finale usa una misurazione **A/B interleaved nello stesso processo**, che annulla la varianza di macchina.

## 3. Modifiche implementate

### 3.1 Nuovo modulo `lib/adaptiveRender.ts`
- `AdaptiveRenderSettings`: `enabled`, `nearDistanceScales`, `farStride`, `cullBehindCamera`, `cullMarginUnits`.
- `AdaptiveRenderState`: contatore frame, dettaglio/capacità/`viewKey` per invalidazione globale.
- `AdaptiveRenderCounters`: `updated`, `skipped`, `culled`, `lodNear`, `lodFar`.
- `farUpdateDue(frame, slot, stride)`: rotazione deterministica senza code né arretrati.

### 3.2 `components/simulation/planet3d/creatureInstancing.ts`
- Percorso adattivo **opt-in**: se `refs.adaptive` è assente o `enabled:false`, il codice esistente resta identico (verificato dai 85 test G3 precedenti).
- **Classificazione LOD**: distanza dal centro camera in scale di taglia (`nearDistanceScales`); vicine = ogni frame, lontane = 1 ogni `farStride`.
- **Culling dietro la camera**: dot product con la direzione di vista e margine configurabile; `zeroCreatureSlots()` azzera le matrici delle creature uscite dalla visuale per evitare "fantasmi" nei buffer persistenti.
- **Invalidazione immediata** (anche per creature che verrebbero saltate):
  - cambio identità del render plan (`planFor` ritorna un nuovo oggetto);
  - cambio sorgente anatomica;
  - cambio specie/taglia/geni nel percorso legacy;
  - cambio `detail`, `capacity` o `viewKey` (fov/aspect → viewport/zoom).
- **Rientro in vista immediato**: `wasVisible:false → true` forza la riscrittura nello stesso frame.
- **Nessun arretrato**: lo stato visivo (motion, fase, living) viene aggiornato ogni frame; il salto riguarda solo la scrittura dei buffer GPU. Quando arriva il turno, la creatura usa i dati correnti.
- Riutilizzo del piano già letto per l'invalidazione (evita un doppio `planFor` per creatura).
- Contatori adattivi esposti in `CreatureRendererStats`.

### 3.3 `components/simulation/Planet3DView.tsx`

## 7. Test non eseguiti / limiti hardware e residui

| Voce | Stato | Motivo |
|---|---|---|
| FPS reali | **non misurati** (`null`) | Il benchmark gira in Node senza WebGL; l'inverso del tempo di una funzione isolata non è un FPS e non è stato presentato come tale |
| Frame time GPU / upload GPU / fill-rate | **non misurati** (`null`) | Nessun `WebGLRenderer` in Node; `gpuBytes: null` |
| Dispositivo mobile fisico | **non eseguito** | Ambiente senza dispositivo fisico; l'override viewport in sessioni precedenti non attivava il layout immersivo (`visualViewport.width` restava 912) |
| Screenshot browser | **non riuscito** | Finestra desktop non visibile: `browser.screenshot` richiede tab focused in finestra visibile |
| Heap snapshot browser | **non riuscito** | Oltre il limite di trasferimento 5 MiB (limitazione già nota) |
| Viewport simulato | **non eseguito in browser** | Verificato con test automatico (test 9: `aspect`/`fov` → refresh) |
| Benchmark GPU/browser | **non eseguito** | Solo CPU main-thread Node |

**Residui noti:**
- Il culling implementato è **dietro il piano della camera** (con margine), non un frustum culling completo: le creature lateralmente fuori campo ma davanti alla camera vengono ancora aggiornate. È una scelta deliberata per evitare popping sui bordi e per non dipendere da matrici di proiezione nel loop caldo.
- `viewKey` usa `aspect * 1000 + fov`: cambi di viewport molto piccoli potrebbero non superare la soglia di risoluzione effettiva del float; il test con `aspect 1.6 / fov 60` passa.
- Il percorso adattivo è **opt-in**; il comportamento predefinito del branch resta G3 (ora con `adaptive.enabled:true` nel solo `Planet3DView`, quindi attivo in produzione, ma disattivabile da `refs.adaptive`).
- Nessun file sotto `simulation/**` è stato modificato.
